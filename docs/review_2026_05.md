# Code Review: `nicegui-aggrid-crud`
## Pre-Acorn Trail Modernisation Review

**Reviewed against:** NiceGUI 3.x (`llms.txt` patterns), AG Grid 34.x, SQLModel 0.0.16+  
**Purpose:** Identify simplification opportunities, design/behaviour separation, and `@ui.refreshable` applicability before incorporating into Acorn Trail.

---

## Executive Summary

The codebase is solid, well-documented, and the 10 AG Grid/NiceGUI gotchas remain valid and should be preserved. However, three categories of improvement are warranted before adoption into Acorn Trail:

1. **Design/behaviour entanglement** — hardcoded colours, sizes, and CSS live inside the component. Acorn Trail needs to define a design policy that `CRUDGrid` inherits, not the other way around.
2. **`@ui.refreshable` applicability** — the current `refresh()` method is mostly correct but bypasses NiceGUI's own element management. There is a better pattern available.
3. **Minor simplifications** — the new `llms.txt` patterns reveal a few places where we are working harder than necessary.

---

## Section 1: Design / Behaviour Entanglement

This is the most important issue to resolve before Acorn Trail adoption.

### What is embedded in the component today

**In `crud_grid.py`:**

```python
# Hardcoded in build() — not configurable
_GRID_CSS = """
.edited-cell {
    background-color: #fff3cd !important;   ← amber, light-mode assumption
    border-left: 3px solid #ffca2c !important;
}
"""

# Also in build():
ui.add_css(f"""
    .ag-theme-balham {{                      ← theme hardcoded
        --ag-font-size: 12px;               ← hardcoded
        --ag-row-height: 26px;              ← hardcoded
        --ag-header-height: 32px;           ← hardcoded
    }}
    .{self._grid_class} {{
        --ag-header-background-color: {self._header_colour};   ← passed in but no default system
    }}
""")

# Toolbar buttons have no style customisation
ui.button("REFRESH", icon="refresh", ...)   ← uses NiceGUI default colour
ui.button(self._label_delete, ...).props("color=negative")   ← hardcoded
```

**In `columns.py`:**

```python
# Alignment and formatting are pure design decisions:
if inner_type in _NUMERIC_TYPES:
    col["type"] = "numericColumn"   ← right-aligns numbers — correct behaviour
                                       but the formatter is implicit in AG Grid's
                                       numericColumn type which we cannot override
```

### The Problem

Acorn Trail will be dark-themed (consistent with the `tearsheet.py` reports). The current defaults are light-mode. If `CRUDGrid` is imported as-is, the dirty-cell amber highlight (`#fff3cd`) will be invisible on a dark background, and `ag-theme-balham` is a light theme.

More broadly: **the component decides what it looks like** rather than **the host app deciding and the component complying**.

### Proposed Solution: `GridDesignPolicy`

Introduce a dataclass that captures every design decision separately from behaviour. `CRUDGrid` accepts one as an optional parameter; if none is provided it uses a sensible default. Acorn Trail defines its own policy once and passes it everywhere.

```python
# acorn_trail/design/grid_policy.py

from dataclasses import dataclass, field


@dataclass
class GridDesignPolicy:
    """
    All visual/layout decisions for a CRUDGrid instance.
    Separate from behaviour so the host app controls the look.

    Acorn Trail defines ONE instance of this and passes it to every grid.
    """
    # AG Grid theme
    ag_theme: str = "ag-theme-balham-dark"      # dark by default for Acorn Trail

    # AG Grid CSS variables
    font_size:     str = "12px"
    row_height:    str = "28px"
    header_height: str = "32px"

    # Default header colour (overridden per-grid for visual distinction)
    header_colour: str = "#2a2a3e"

    # Grid container height
    height: str = "600px"

    # Dirty cell highlight (amber works on dark AND light with right contrast)
    dirty_cell_bg:     str = "#3a3000"          # dark amber for dark theme
    dirty_cell_border: str = "#ffca2c"

    # Toolbar button colours (Quasar colour names)
    btn_refresh_colour: str = "primary"
    btn_new_colour:     str = "positive"
    btn_upload_colour:  str = "primary"
    btn_delete_colour:  str = "negative"

    # Button labels
    label_new:    str | None = "NEW"
    label_upload: str | None = "UPLOAD"
    label_delete: str | None = "DELETE"


# Acorn Trail's canonical policy — imported once, used everywhere
ACORN_TRAIL_GRID_POLICY = GridDesignPolicy(
    ag_theme       = "ag-theme-balham-dark",
    header_colour  = "#1e2235",
    dirty_cell_bg  = "#3a3000",
    dirty_cell_border = "#ffca2c",
    btn_refresh_colour = "primary",
)
```

Then `CRUDGrid.__init__` accepts:

```python
from acorn_trail.design.grid_policy import GridDesignPolicy, ACORN_TRAIL_GRID_POLICY

class CRUDGrid:
    def __init__(
        self,
        table_model,
        load_rows,
        submit_row,
        ...
        design: GridDesignPolicy | None = None,   # ← NEW
    ):
        self._design = design or GridDesignPolicy()   # neutral default if standalone
```

And `build()` uses `self._design` everywhere instead of hardcoded values:

```python
def build(self):
    ui.add_css(f"""
        .edited-cell {{
            background-color: {self._design.dirty_cell_bg} !important;
            border-left: 3px solid {self._design.dirty_cell_border} !important;
        }}
        .ag-theme-balham, .ag-theme-balham-dark {{
            --ag-font-size: {self._design.font_size};
            --ag-row-height: {self._design.row_height};
            --ag-header-height: {self._design.header_height};
        }}
        .{self._grid_class} {{
            --ag-header-background-color: {self._design.header_colour};
        }}
    """)
    ...
    .classes(f"{self._design.ag_theme} {self._grid_class}")
    .style(f"height: {self._design.height};")
```

**Result:** `nicegui-aggrid-crud` becomes purely behavioural. Acorn Trail's design lives in one file. If you ever want a light-mode version, you swap one policy object.

## Section 2: `@ui.refreshable` — Where it Helps and Where it Doesn't

### The current `refresh()` pattern

```python
def refresh(self) -> None:
    self.grid.options["rowData"] = self._load_rows()
    self.grid.update()
    self._dirty_rows.clear()
    self._selected_row_index = None
    ui.run_javascript(f"clearDirtyKeys_{self._dirty_js_name}()")
    self.grid.run_grid_method("refreshCells", {"force": True})
```

This is actually **correct for the grid itself**. AG Grid has its own internal row model — `grid.update()` is the right way to push new data into it without destroying the Vue component. Using `@ui.refreshable` on the grid itself would destroy and recreate the AG Grid instance, losing scroll position, column state, and filter state. The current approach is the right one.

### Where `@ui.refreshable` DOES help: the toolbar and summary row

Currently the toolbar buttons are built once in `_build_toolbar()`. If you later add a "selected row count" badge or a "X dirty rows" indicator to the toolbar, you will need to update those labels manually. A `@ui.refreshable` on just the toolbar summary section is cleaner:

```python
@ui.refreshable
def _build_status_bar(self) -> None:
    """Small status bar above the grid — dirty count, selected row info."""
    if self._dirty_rows:
        ui.badge(f"{len(self._dirty_rows)} unsaved", color="warning")
    if self._selected_row_index is not None:
        ui.badge(f"Row {self._selected_row_index + 1} selected", color="info")
```

Then call `self._build_status_bar.refresh()` after `_on_cell_value_changed` and `_on_cell_clicked`. This is a clean use of `@ui.refreshable` — a small reactive subtree that doesn't touch the grid.

### `@ui.refreshable` verdict

| Area | Use `@ui.refreshable`? | Reason |
|---|---|---|
| The AG Grid itself | ❌ No | Destroys grid state; `grid.update()` is correct |
| Toolbar buttons | ❌ No | Static — build once |
| Status bar / dirty count | ✅ Yes | Small reactive subtree |
| Summary footer (totals row) | ✅ Yes | Updates when data changes |
| Linked detail panel (image/label) | ✅ Yes | Driven by row selection |

## Section 3: Simplifications from `llms.txt` Patterns

### 3.1 Async — the biggest risk for Acorn Trail

The current `load_rows`, `submit_row`, and `delete_row` callables are all **synchronous**. This was fine for the demo (SQLite is fast), but in Acorn Trail:

- `load_rows` will hit `PMSEngine` (database queries)
- `submit_row` will write to the database
- yfinance price fetching will hit the network

Synchronous calls inside NiceGUI event handlers block the entire event loop for all users. The fix is to support async callables:

```python
import asyncio
from nicegui import background_tasks

async def _async_refresh(self) -> None:
    """Async-safe refresh — runs load_rows in a thread if synchronous."""
    if asyncio.iscoroutinefunction(self._load_rows):
        rows = await self._load_rows()
    else:
        rows = await asyncio.to_thread(self._load_rows)
    self.grid.options["rowData"] = rows
    self.grid.update()
    ...
```

**Recommendation:** Add an `async def refresh()` alongside the sync version, or make the component detect whether `load_rows` is a coroutine function and handle both.

### 3.2 Multi-user state safety

The current `self._dirty_rows`, `self._selected_row_index`, and `self._autofitted` are instance variables — one per `CRUDGrid` instance. This is **correct** as long as each `@ui.page` creates a fresh `CRUDGrid` instance per user visit, which it will if `CRUDGrid` is instantiated inside the page function:

```python
@ui.page('/holdings')
def holdings_page():
    grid = CRUDGrid(...)   # ← fresh instance per user ✓
    grid.build()
```

The risk is if someone instantiates `CRUDGrid` at module level (outside a `@ui.page`). This should be documented explicitly as a warning.

### 3.3 `ui.add_css` called on every `build()`

```python
def build(self) -> "CRUDGrid":
    ui.add_css(_GRID_CSS)          # ← called every time build() is called
    ui.add_head_html(_dirty_js)    # ← same
```

`ui.add_css` is idempotent in NiceGUI (duplicate CSS is harmless), but `ui.add_head_html` injects a new `<script>` block every time `build()` is called on a page with multiple grids. For Acorn Trail, where multiple grids may appear on one page, the per-instance JS is already scoped correctly via `_dirty_js_name`, so this is not a bug — but it is worth noting. A small guard can be added:

```python
_css_injected: set[str] = set()   # module-level set

def build(self):
    if "base" not in _css_injected:
        ui.add_css(_GRID_CSS)
        _css_injected.add("base")
    # Per-instance JS is always injected (it's scoped by _dirty_js_name)
    ui.add_head_html(_dirty_js)
```

### 3.4 `_on_cell_double_clicked` — the `json.dumps` gap

```python
ui.run_javascript(f"""
    ...
    if (val) val.textContent = '{new_value}';
    ...
""")
```

`new_value` here is a datetime string like `2024-01-15T14:32:00` — safe in this specific case. But the README's own gotcha #10 warns about this. The defensive fix (already noted in the README, should be applied in code):

```python
import json
safe_value = json.dumps(str(new_value))
ui.run_javascript(f"if (val) val.textContent = {safe_value};")
```

### 3.5 `header_colour` / `height` duplication

Currently these exist as both top-level constructor parameters AND will exist inside `GridDesignPolicy` after refactoring. During the refactor, remove the top-level parameters entirely — they should live only in `GridDesignPolicy`. This makes the constructor signature cleaner and avoids the question of "which one wins if both are specified?"

## Section 4: What to Keep Exactly As-Is

The following are correct, hard-won, and should survive the refactor unchanged:

| Item | Why it must stay |
|---|---|
| `cellClicked` not `rowClicked` | Circular JSON serialisation bug in `rowClicked` (Gotcha #5) |
| Per-instance `_dirty_js_name` | Prevents dirty highlight bleeding across grids (Gotcha #8) |
| `_autofitted` boolean guard on `firstDataRendered` | Re-fires on every `grid.update()` (Gotcha #6) |
| `cast_row_types` before `submit_row` | JSON round-trip loses `Decimal`/`int`/`datetime` precision |
| `grid.update()` not `applyTransaction` | `getRowId` cannot be set via NiceGUI (Gotcha #5) |
| Colon-prefix `:valueFormatter` | Plain string form not evaluated as JS in NiceGUI 3.x (Gotcha #4) |
| `grid.on("cellValueChanged", ...)` not `{"function": ...}` | NiceGUI intercepts `onCellValueChanged` (Gotcha #1) |
| DOM direct write for `_time`/`_date` columns | AG Grid row model not reliably accessible from NiceGUI context (Gotcha #8) |
| `json.dumps()` for JS string injection | Prevents breakage on values with quotes/special chars (Gotcha #10) |

## Section 5: Proposed File Structure for Acorn Trail

```
acorn_trail/
├── design/
│   ├── __init__.py
│   ├── grid_policy.py          ← GridDesignPolicy dataclass
│   ├── theme.py                ← Acorn Trail colour tokens, typography
│   └── ACORN_TRAIL_POLICY.py   ← canonical policy instance (or in grid_policy.py)
│
├── components/
│   └── grid/
│       ├── __init__.py
│       ├── crud_grid.py        ← CRUDGrid (design-agnostic, accepts GridDesignPolicy)
│       ├── columns.py          ← unchanged
│       └── formatters.py       ← unchanged + json.dumps fix
```

`nicegui-aggrid-crud` then becomes a **reference implementation** and test bed. Acorn Trail carries its own copy of the three core files (as the README already recommends), modified with:

1. `GridDesignPolicy` integration
2. Async-safe `refresh()`
3. `@ui.refreshable` status bar
4. `json.dumps` fix applied in code not just docs
